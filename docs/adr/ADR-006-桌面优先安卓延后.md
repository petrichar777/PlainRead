# ADR-006: 桌面优先，安卓延后至 1.0 之后的版本迭代

## Status

**Accepted**（2026-10-11）—— 项目 owner 拍板：「安卓端先不做，留做后续版本迭代升级功能；先把桌面端功能完成解决。」
同日 owner 已完成 **M0 桌面端人工验收**（`npm run tauri dev` 全流程），结果无问题。

## Context

原排期（[03-里程碑与验收清单](../03-里程碑与验收清单.md)）把「安卓构建链在 M0 末尾打通」列为排序原则第一条，
理由是 R3：安卓交叉编译是唯一可能连续数天定位不到的环境问题，应尽早暴露。

实际进展到 M0 末尾时，事实前提发生了变化：

1. **桌面端已全部通过**：自动化验收（29 项 Rust 测试、typecheck、lint、build、clippy、fmt）全绿，
   人工验收（窗口启动、IPC 状态胶囊、内核自检、中文往返）也已由 owner 实测通过。
2. **安卓环境一无所缺地卡住 M0 收尾**：本机无 Android SDK / NDK / adb / Rust Android targets，
   且安装必须由本机所有者手动操作（GUI 安装程序 + 授权）。
3. **M0 的核心价值已经兑现**：IPC 契约链路（tauri-specta 自动生成 + 契约守卫测试）与双 crate 工作区
   均已打穿——这正是「安卓前置」真正想保护的东西。剩余的安卓侧验收项
   （`android init` / `android dev` / APK）验证的是 Tauri 安卓链路本身，**不阻塞任何桌面端里程碑（M1–M3、M5）**。

继续把 M0 卡在安卓环境上，等于让唯一阻塞项阻塞所有后续工作；而把它后置，桌面端 M1 可以立即开工，零等待。

## Decision

**D1. 范围调整：1.0 只交付 Windows 桌面端；安卓（手机 / 平板）整体延后到 1.0 之后的首个迭代版本。**

- M0 的安卓侧验收项（`android init` / `android dev` / `build --apk` / 真机验证）标记为 **⏸ 延后**，不计入 1.0 完成条件。
- **M4（安卓落地）整体顺延**：推迟到 M5（桌面打磨与交付）之后，作为 1.x 的第一个里程碑。
- M0 视为**桌面侧完成**（2026-10-11），不再因安卓环境而挂起。

**D2. 架构与代码不因 D1 做任何删改。**

- `reader-core` 的领域模型、存储设计、导入管线本就与平台无关；
- Tauri 2 外壳保留 `gen/android/` 的生成能力，`scripts/` 下的安卓脚本
  （`check-android.sh` / `setup-android.sh` / `build-android.sh`）**原样保留**，
  作为 1.x 启动安卓迭代时的现成入口；
- [04-环境准备与M0前置检查](../04-环境准备与M0前置检查.md) 中的安卓安装指南**保留不删**——
  它就是未来换机或装环境时的操作手册。

**D3. 里程碑顺序调整为：M0（桌面侧）→ M1 → M2 → M3 → M5 → M4（安卓）。**

M5 原文中的 `armeabi-v7a 补齐`一项随 M4 一并顺延；其余 M5 项（大书性能、错误处理、平板断点适配等）
按桌面口径执行，其中平板适配在桌面端对应为窗口宽度断点，含义不变。

## Consequences

### 收益

- **M1 立即开工**，不再被环境安装阻塞；1.0 可用时间显著提前。
- R3（安卓交叉编译环境风险）从「当前风险」降级为「已文档化的未来工作」，风险敞口缩小到 1.x 期间。
- 排期重心与 owner 当前意愿一致：先把桌面端功能做完整、做好用。

### 代价与遗留

- **违背了原排序原则第一条**（安卓前置暴露环境风险）。接受该代价的理由：M0 核心目标（IPC 契约）
  已在桌面侧兑现，安卓链路的验证价值只剩「Tauri 安卓构建本身」，届时再暴露的损失可控。
- **跨端验证被推迟**：M1–M3 期间做出的实现决策（如章节读取、设置持久化、事件推送）若存在安卓差异，
  将在 1.x 才被发现。缓解：两条核心不变式（不丢字 / 进度往返）与「IPC 粗粒度」「永不整书入内存」
  等平台无关约束继续全程守卫，`reader-core` 保持在无窗口环境下可完整单测。
- 安卓侧的 M0 验收清单**原样保留在 03 文档中**，不删不改，1.x 启动时直接续用。
