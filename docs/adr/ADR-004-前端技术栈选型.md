# ADR-004: 前端技术栈选型

## Status

**Accepted**（2026-10-09）—— 项目 owner 确认按本 ADR 的推荐方案执行：**React 19 + TypeScript + Vite + Tailwind CSS + shadcn/ui**。

## Context

[ADR-003](ADR-003-采用Tauri2作为跨端外壳.md) 决定 UI 层使用 Web 技术栈。随之而来的是前端框架与样式方案的选型。

约束条件（按优先级）：

1. **UI 美观度是项目的首要质量属性**（项目 owner 明确要求「必须做得好看且好用」）
2. **单人开发、后端技术背景为主**（Java / Rust），前端经验不是强项
3. **界面规模小但要求精致**：书架、阅读、目录、设置共四屏
4. **有真实性能诉求的一处**：目录页在 3000 章规模下需要虚拟化滚动
5. **Tauri 场景是纯静态前端**，不需要 SSR / SEO / 服务端渲染

排除项：

| 方案 | 排除理由 |
|---|---|
| **Next.js / Nuxt / SvelteKit** | SSR / SSG / 服务端路由在 Tauri 中毫无用处，只会增加构建复杂度与心智负担 |
| **React Native / Flutter** | 与 Tauri 路线冲突（这是上一轮被放弃的方向） |

## Decision

**推荐：React 19 + TypeScript + Vite + Tailwind CSS + shadcn/ui**

### 关键论证

**① 为什么是「框架」而不是纯 vanilla**

只有一处真实需求必须用框架：目录页的 3000 章虚拟滚动，以及书架列表的增删改响应式更新。纯 DOM 操作可以做到，但会把状态同步逻辑写散，而这类手工同步恰恰是最容易出错、最难保证精致度的地方。用一个轻量框架换取声明式 UI 是划算的。

**② 为什么是 React 而不是 Vue / Svelte**

这一条的实质理由只有一个：**UI 组件生态**。

项目 owner 的首要诉求是"好看"。而当下能最快达到"精致好看"的路径是 **shadcn/ui** —— 它不是传统组件库（不是 `npm install` 一个黑盒），而是**把源码复制进你的项目**的一组高质量、强可定制组件，构建在 Radix UI（无障碍原语）与 Tailwind CSS 之上。

关键点：**shadcn/ui 的源码是 React 的。** 选 Vue 或 Svelte 就意味着放弃这条最省力的"精致化"路径，需要自己从零搭组件层，或者使用定制能力更弱的传统组件库。

React 的次要优势：遇到问题时可检索的资料量最大（对不熟悉前端的开发者，这一点在关键时刻很重要）。

**③ 为什么显式选 TypeScript**

因为 IPC 边界的存在。Rust 侧的类型需要映射到前端，TS 能在编译期抓出契约漂移，这是双语言架构下最重要的护栏之一。

**④ 为什么是 Tailwind CSS**

- 设计令牌（间距、字号、圆角、色板）天然统一 → 直接服务于"视觉精致度"
- 换主题只需换令牌，不需要改组件
- 不需要为类名想名字，减少决策疲劳
- 与 shadcn/ui 是同一套体系

**⑤ 不引入全局状态库**

四屏应用的状态量很小：书库列表、当前书、当前章节、设置、主题。React 内置的 `useState` / `useReducer` + Context 足够。**不引入 Redux / Zustand / Jotai**——这是本项目的反过度设计原则。

唯一例外：如果阅读器的翻页状态（当前页索引、动画中标志、预加载缓存）变得复杂，可局部引入一个轻量 store，但这是观察到问题之后再做的事。

### 被放弃的候选

| 候选 | 优点 | 放弃理由 |
|---|---|---|
| **Vue 3 + TS** | 单文件组件体验好、上手平缓、中文资料多 | 放弃 shadcn/ui 生态；定制组件要用更弱的方案 |
| **Svelte 5 + TS** | 编译期框架、运行时最小、性能好、代码简洁 | 生态最小；组件库选择少；对前端不熟悉者出问题时最难搜到答案 |
| **纯 vanilla + Tailwind** | 构建最简、无框架心智 | 虚拟滚动与响应式状态同步要手写，与"精致"目标冲突 |
| **传统组件库**（Element Plus / Ant Design / MUI 等） | 开箱即用组件多 | 视觉风格强绑定、定制成本高，容易做出"后台管理系统"感，与阅读器需要的克制审美不符 |

## Consequences

### 变得更简单

- 视觉精度的实现路径最短（Tailwind 令牌 + shadcn/ui 组件）
- 参考资料充足，遇到问题容易解决
- 类型安全覆盖 IPC 边界

### 变得更复杂

- 需要掌握 JSX / hooks / TS 三件套（对后端背景者有一定学习曲线）
- Node 工具链进入构建流程
- 依赖树规模变大（前端生态的固有代价）

### 迁移成本（低，作为风险对冲）

前端框架被隔离在项目根目录的 `src/` 下，与 `src-tauri/`（Rust）和 `crates/`（内核）完全解耦。**若要更换前端框架，改动范围局限在 `src/` 目录内**，Rust 侧的命令接口与数据契约不需要任何修改。

这是本 ADR 敢于给出推荐而不坚持投票的原因：选错的代价可控。

## 备注

- 若最终选择 Vue 或 Svelte，架构文档 §4（IPC 契约）与 §7（阅读器前端实现）中的**设计原则不变**，仅具体语法与组件实现不同。
- 阅读器最核心的排版能力（CSS 多列分页、字符偏移锚点、`line-break: strict`）在任何框架下都是同一套 CSS 与 Web API，不依赖框架选择。
