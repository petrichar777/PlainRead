# ADR-001: UI 框架与渲染技术路线

## Status

**Superseded by [ADR-003](ADR-003-采用Tauri2作为跨端外壳.md)**（2026-10-09）

> 本 ADR 的结论已被推翻，但**完整保留**作为决策留痕。
> 推翻的原因、原论证中的两处判断偏差及修正过程，见下方「复议记录」章节。

## Context

需要一套 GUI 技术栈，用 Rust 实现一个阅读器，同时运行在 **Windows 桌面**、**安卓手机**、**安卓平板** 上。

约束条件（按优先级）：

1. **纯 Rust**：用户明确要求「用 Rust 开发」，UI 层不希望退化为 Web 前端
2. **阅读器的排版是核心体验**：字号、行距、字距、页边距、首行缩进、中文断行规则都需要**像素级控制**
3. **中文正文渲染质量**：需要字体回退（生僻字、繁体字、emoji）、标点处理
4. **单人开发、长期维护**：技术栈的社区体量与迭代活跃度直接影响能否解决问题
5. **许可干净**：个人项目，但不想引入署名义务或未来的商业授权闸门

评估时间点：**2026-10**。

候选方案及其在该时间点的实际状态：

| 框架 | 版本 | 安卓支持状态 |
|---|---|---|
| egui / eframe | 0.36.1（2026-08） | 官方后端 `android-activity`，支持 NativeActivity 与 GameActivity |
| Slint | 1.17（2026-06） | 官方支持，含 safe-area-inset 与 virtual-keyboard 内置属性 |
| Dioxus | 0.7（2025-09） | 支持，但 WGPU 原生渲染器标注为实验性 |
| Tauri 2 | 2.x | 官方支持，UI 走系统 WebView |

## Decision

**采用 `egui 0.36` + `eframe` 作为 UI 框架，`cosmic-text` 作为独立于 UI 的排版内核。**

### 关键论证

**① 排版控制力 —— 决定性因素**

阅读器的产品价值几乎全部落在排版细节上。egui 是全自绘的立即模式框架，**每一个像素都由应用代码决定**，不存在"框架的 ScrollView 不让你调行高"这类博弈。Slint 的 `Flickable` / `ListView` 能省掉滚动与惯性动画的实现，但代价是排版细节需要绕过或对抗框架的组件语义。

**② "立即模式不适合长列表"这个已知缺点在本项目不成立**

这是 egui 最常被引用的短板。但阅读器天然采用**分页模型**而非无限滚动模型——一页约 400–600 个字形，重绘成本可忽略；静止时通过 `request_repaint_after` 进入空闲状态，不消耗 GPU 与电量。**该缺点被应用形态自然规避。**

**③ 许可零摩擦**

egui 为 `MIT OR Apache-2.0`。Slint 采用 GPLv3 / Royalty-Free / Commercial 三选一：Royalty-Free 对桌面与移动的闭源应用免费，但**要求保留 "Made with Slint" 署名**，且授权结构为未来留下不确定性（例如嵌入式场景需按设备计费）。对本项目"纯粹、无附加条件"的诉求而言，MIT/Apache 更省心。

**④ 排版内核与 UI 解耦，是对冲框架风险的保险**

`cosmic-text` 不依赖任何 GUI 框架。把分页写成纯函数 `(text, spec) -> pages`，意味着：

- 可以在没有 GPU、没有窗口的环境下做**单元测试**——这是阅读器正确性的主要保障；
- 一旦将来要换 UI 框架，**排版引擎与全部业务逻辑原样保留**。

即使 ③ 的许可判断有偏差，④ 也把迁移成本压到"重写 UI 层"。

### 明确接受的代价

| 代价 | 缓解措施 |
|---|---|
| 安全区 / 刘海 / 状态栏 inset 需手写 | M4 专项处理；页面内边距做成常量表，配合真机 + 模拟器双验证 |
| 软键盘弹起不自动避让 | 1.0 仅在搜索场景需要输入法，而搜索属 2.0；风险不在关键路径 |
| 无内置文件对话框 | `Platform` trait 隔离；桌面用 `rfd`，安卓用 `robius-file-picker` |
| 无声明式布局 DSL，UI 即 Rust 代码 | 对单人项目而言反而减少了一层概念转换成本 |
| 框架迭代快，API 可能变动 | workspace 层面锁定 `=0.36`；升级作为独立任务评估 |

## Consequences

### 变得更简单

- 排版细节完全可控，能实现"中文小说阅读器该有的样子"（首行缩进两字、标点禁则、行距可调）
- 分页引擎可纯函数单测，重构有信心
- 依赖树全宽松许可，未来开源或闭源分发都无阻碍
- 桌面与安卓共用同一套 UI 代码，只有壳层（`app-desktop` / `app-android`）不同

### 变得更困难

- 需要自己实现滚动容器、惯性、翻页动画等基础设施（Slint 部分内置）
- 安卓端输入法与安全区需手动适配，且这部分**无法只靠桌面开发验证**
- 立即模式的"状态即数据"心智模型要求设计得当，否则容易出现 UI 状态散落

### 被明确排除的方案与理由

| 方案 | 排除理由 |
|---|---|
| **Slint** | 移动端适配最省事（safe-area / virtual-keyboard 内置），但许可结构带来署名义务与未来不确定性；且排版深度定制的灵活性低于自绘。**若后续更看重"少写移动端适配代码"，这是一个合理的替换目标**——得益于分层设计，迁移只影响 `reader-ui` 与 `app-android` |
| **Tauri 2** | 桌面 + 移动支持最成熟，但 UI 层是 HTML/CSS，直接违反"纯 Rust"约束；安卓端 WebView 的内存与启动开销也不符合"纯净轻量"的定位 |
| **Dioxus 0.7** | 单代码库跨端最省心、Subsecond 热补丁体验极佳，但 WGPU 原生渲染器仍标注实验性，移动端稳定性不足以支撑 1.0。**列为 2.0 之后的观察对象** |

## 备注

- 若未来需要更专业的文本排版能力（如竖排、注音、复杂文种），可评估在 `cosmic-text` 之上自建排版层，或引入 Servo 的 `layout` 组件——但这不属于 1.0 范围。
- 参考 `01-可行性分析.md` §2.1 的完整对比矩阵。

## 复议记录（2026-10-09）

**触发**：项目 owner 提出质疑——「前端可以用 CSS，Tauri 2 有其他不行的理由吗？例如运行速度效率不够高等等」。

本案的原始论证存在两处问题，核查后修正如下。**保留原始结论不变，但支撑它的理由需要重写。**

### 一、被推翻的理由

#### ① 「排版靠 CSS，控制力不足」——判断错误

初版把 UI 层不使用 Rust 表述为「排版靠 CSS」，隐含地把它当作缺点。**对中文阅读器恰恰相反，这是优点**：

| 能力 | 浏览器引擎 | 自绘路线（cosmic-text） |
|---|---|---|
| CJK 断行禁则 | 引擎内置，任何 WebView 版本都有 | UAX #14 覆盖（见下） |
| 字体回退（生僻字/繁体/emoji） | 全自动 | 需维护 `fontdb` 字体链 |
| 标点挤压 `text-spacing-trim` | Chrome 123+ 原生 | **需自研** |
| 中西文自动间距 `text-autospace` | Chrome 120+ | **需自研** |
| 竖排 `writing-mode: vertical-rl` | 直接可用 | **做不了** |
| 样式迭代速度 | 改 CSS | 改自绘代码 |

#### ② 「安卓端 WebView 的内存与启动开销不符合纯净轻量定位」——证据不足

这条当初是凭印象写的，没有数据支撑。补充实测量级后，**该表述不准确**：

| 指标 | Tauri 2 移动端（中端安卓） | 判断 |
|---|---|---|
| 冷启动 | 约 300 ms | ✅ 不构成问题 |
| 常驻内存 | 约 110 MB | ⚠️ 比自绘路线高约 50–70 MB |
| APK 体积 | 很小 | ✅ 不构成问题 |

所以真正的问题**不是"轻不轻量"，而是一个约 50–70 MB 的内存差**，且只在 2–3 GB 低端设备上才有实际影响。

### 二、同时被推翻的、本项目自身的风险评级

初版把「中文禁则需自研」列为 **R1（概率：高）**。复核发现这同样是**高估**：

- `cosmic-text` 的断行基于 `unicode_linebreak` crate，它实现的是 **UAX #14**；
- UAX #14 通过 `CL`（Closing Punctuation，如 `。`）、`OP`（Opening Punctuation，如 `（`）等类别，**已经规定了 CJK 的"标点不得位于行首/行尾"规则**；
- 因此**基础禁则在两条路线上都是免费的**。

自研部分只剩下"标点挤压"与更精细的禁则调整，风险等级由 **高 → 中**。

**结论：排版质量不构成两条路线之间的区分度。** 初版把它当作 egui 的劣势、Tauri 的优势，是双重的判断偏差。

### 三、修正后仍然成立的理由

| # | 顾虑 | 严重度 | 说明 |
|---|---|---|---|
| 1 | **「用 Rust 开发」的性质改变** | —— | 项目变成「Rust 内核 + HTML/CSS 前端」。这不是技术优劣问题，是项目定位问题，**只能由 owner 拍板** |
| 2 | WebView 版本碎片化 | **中** | 老设备的系统 WebView 可能长期未更新，`text-spacing-trim` 等新特性拿不到；且需在构建层把 target 降级（如 `chrome90`）以避免语法/布局崩坏 |
| 3 | 移动端生态与社区案例薄 | **中** | 已有真实项目（SwarmNote）在验证后保留 Rust 内核、但换掉了 Tauri 移动端外壳，原因是移动插件生态与文件系统复杂度 |
| 4 | 内存 | 中低 | 约 110 MB vs 自绘路线的 50 MB 量级 |
| 5 | 双语言栈与 IPC 边界 | 中低 | 需设计 IPC 协议、维护两套心智。**对阅读器影响较小**：翻页不产生 IPC，一页文本由 Rust 算好后一次性下发，不存在高频 JSON 往返 |
| 6 | 安卓侧双侧调试 | 低 | 需同时处理 WebView 与 Rust 两侧 |
| 7 | Node/npm 工具链 | 低 | 与「纯 Rust 构建」的工程哲学冲突 |
| 8 | `hanging-punctuation` 不被 Chromium 支持 | 低 | 悬挂标点做不了（仅 Safari 支持） |

### 四、两条路线的风险分布

初版只比较了"能力有无"，忽略了**风险性质**的差异。这其实是更有决策价值的一个维度：

| | egui 路线 | Tauri 路线 |
|---|---|---|
| 难度集中在 | 排版引擎 + 安卓原生适配 | WebView 版本碎片 + 双语言边界 |
| 技术深度 | 深 | 浅 |
| 工作量 | 大 | 小 |
| 不确定性来源 | **全部内部可控** | 部分来自外部（设备 WebView 版本不可控） |
| 可测试性 | 排版可纯函数单测、结果可复现 | 排版结果由引擎决定，跨设备不可复现 |

### 五、修正后的结论

**维持「选 egui」的原结论，但性质从「Tauri 不可行」降级为「这是一次定位取舍」。**

真正的问题不是"Tauri 行不行"，而是：

> **这个项目的价值，是"做出来一个好用的阅读器"，还是"用 Rust 从零做一个原生的跨端应用"？**

- 若答案是**前者** → Tauri 2 是合理甚至更快的选择，本 ADR 应当被推翻，另立 ADR-003。
- 若答案是**后者** → 维持 egui。

### 六、一个可以推迟决策的事实（重要）

`reader-core` 的内容——领域模型、编码识别、文本规范化、章节切分、redb 存储、导入管线——**在两条路线上 100% 复用**。分页引擎只在 egui 路线需要。

因此这个决策**不必现在就做出**：可以先进 M0/M1 的共用部分，等真正要画阅读界面时再定 UI 框架。这是分层架构带来的直接好处。
