# ADR-007: 1.0 功能边界收敛（书签进 / 全局设置页出 / 滚动模式出）

## Status

**Accepted**（2026-10-18）—— 项目 owner 拍板：「那就按照你的建议来」。
本 ADR 只做一件事：把三条原本悬在 `docs/03` 里的「待讨论」条目变成不可复议的结论。

## Context

[03-里程碑与验收清单](../03-里程碑与验收清单.md) 按 UI v2 重排后（v3），1.0 的剩余范围收敛到
**M3（阅读闭环）+ M5（打磨与交付）≈ 8 个业余人日**。此时有三处边界仍然模糊，
每一条都会在开工第一天造成「到底做不做」的反复：

| # | 模糊点 | 卡在哪 |
|---|---|---|
| ① | **书签** | M3 原条目写着「三命令 + UI」，但 [06 §7](../06-UI改版-修改清单.md) 核对发现 **契约里根本没有 bookmark 命令**。做 = 先扩 IPC 契约；不做 = 1.0 没有书签 |
| ② | **全局设置页** | [05 §3.4](../05-UI设计规范系统.md) 已承认「1.0 的设置实际落在诊断页」，但 M3 原条目把「设置页（含 `get_settings`/`save_settings`）」当成交付物 |
| ③ | **分页 ↔ 滚动模式切换** | M3 原条目列为交付物，但它不是"再加一个开关"，而是要重建进度语义（见下） |

判定用的三问（写下来是为了以后复用，不是为了给这三条开脱）：

1. **它是否影响"读一本完整的书"？** —— 影响 = 进 1.0；只是更舒服 = 出。
2. **它的成本是否可逆？** —— 加命令是增量、可回滚；改契约语义或加一套排版模型不是。
3. **它是否引入新的领域语义？** —— 引入 = 风险高（要新不变量 + 新测试），不引入 = 低。

## Decision

**决策 1. 书签进 1.0，方式是「增量扩契约」。**

- 新增 3 条命令：`add_bookmark` / `remove_bookmark` / `list_bookmarks`。
  表（`bookmarks` / `bm_by_book`）与领域模型（`Bookmark`）**都已存在**，缺的只是命令层与 DTO。
- **只追加、不修改既有命令签名** → `gen:bindings` 后 `bindings.ts` 只增不改 → 现有前端零返工。
- UI 入口放顶栏与 dock。**在命令落地之前，这两个位置保持空着**（06 §7：宁可空着也不放假按钮）。
- 判定依据：三问全部指向"进"——书签是阅读行为的组成部分（①），命令增量可逆（②），
  复用既有 `ReadingProgress` 的字符偏移锚点、不引入新语义（③）。

**决策 2. 全局设置页不进 1.0，排到 1.0-rc 之后。**

- 1.0 的外观入口继续由**诊断页**承担（切主题 + 主题记忆 + 自检 + IPC 往返），与 05 §3.4 现状一致。
- `get_settings` / `save_settings` 契约本版不扩；阅读偏好继续走 `localStorage`（`reading-prefs.ts`）。
- 判定依据：诊断页已覆盖"能改主题"这一唯一刚需（①否），而扩契约要把 `ReaderSettings` 抬到 IPC 层、
  牵动持久化归属（②不可逆性偏高），收益撑不起排期风险。

**决策 3. 分页 ↔ 滚动模式切换不进 1.0，冻结至 1.x。**

核心原因不是工期，而是**语义**：分页模型下「页码」= 列位移，可换算成字符偏移，所以进度锚点成立；
滚动模式下「页码」无定义，进度只剩百分比或滚动位置，两者与现有 `章节号 + 字符偏移` 的存储契约不兼容。
要做就得同时给出"滚动模式下的锚点与恢复"新不变量，属于新领域语义（③命中），成本与 D4 对页双栏同级。

覆盖式（clip-path）翻页动画同样不进：v2 只定义 translate 一种（`--ui-dur-page` 220 ms），
再加一种不产生阅读收益，属于典型的"加法的幻觉"。

**决策 4. 本 ADR 的三条结论不可口头推翻。**

出现新证据时要写新 ADR 取代本文件（并在本文件 Status 标 `Superseded by ADR-XXX`），
不在 issue / 聊天 / 代码注释里改口径。

## Consequences

### 收益

- **范围封版**：M3 从「3 条必做 + 1 条可选」变成「3 条必做」，剩余 ≈3 人日可估、可承诺。
- **风险前置**：唯一需要动 IPC 契约的工作（书签）被明确排在 W1，不会在交付前夜才暴露。
- **不留假按钮**：决策 1 的顺序约定（先命令、后 UI）避免了 v2 期间反复出现的「先占位、后补实现」。

### 代价与遗留

- **1.0 没有书签 = 明确的功能缺口**，接受理由是"必须有"而不是"可以不要"；若 W1 结束仍未打通契约，
  则**降级为 1.0 的已知限制并在 README 写明**（不静默删功能、不留假按钮），1.0.x 补齐。
- **设置页缺席带来的可发现性风险**：用户可能找不到主题切换。缓解：诊断页入口在 Rail 底部常驻，
  且 1.0 不做「隐藏式」交互（原则 4：高频操作 ≤ 2 步）。
- **滚动模式缺席**：超长单章（5 万字级）的降级策略（03 · B8）随之失去依托，
  1.0 只能靠分页承担，已在 M5 的性能闸门（P-04/P-08）中重点观测翻页耗时。

### 复议的触发条件（写死，避免凭感觉翻案）

| 结论 | 什么情况下才值得重开 |
|---|---|
| 决策 1 · 书签进 | 不适用——已在做 |
| 决策 2 · 设置页出 | UAT 出现「找不到主题切换 / 找不到字号设置」的实际阻塞反馈（≥2 名非开发者） |
| 决策 3 · 滚动模式出 | 出现"分页在多列极端内容下不可用"的实测证据（而非手感偏好） |
