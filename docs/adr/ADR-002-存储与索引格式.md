# ADR-002: 存储方案与章节索引格式

## Status

**Proposed** —— 待确认后转为 Accepted

## Context

需要为阅读器选择本地持久化方案，存储以下数据：

| 数据 | 规模 | 访问模式 |
|---|---|---|
| 书籍元数据 | 数百本 | 书架页全量扫描，字段少 |
| 章节索引（每本 N 章） | 每本数十到数千章，全书库可达数十万条 | **打开书时必然需要完整列表** |
| 阅读进度 | 每本一条 | 高频写（翻页），需防抖 |
| 书签 | 每本数十条 | 低频写，按书查询 |
| 阅读设置 | 全局 + 每书覆盖 | 低频读写 |

约束条件：

1. 必须能 **交叉编译到 Android**（aarch64 / x86_64），这是硬性门槛
2. 安卓设备存储与电量敏感，写入应尽量少
3. 数据量小（书库总量通常在几十 MB 以内），**不需要复杂查询能力**
4. 单人项目，希望构建链尽量简单

候选方案：

| 方案 | 交叉编译 | 二进制增量 | 查询能力 | 版本 |
|---|---|---|---|---|
| **redb**（纯 Rust） | 零障碍 | ~200–300 KB | KV / B+Tree | 2.6.3 |
| **rusqlite bundled** | 需 NDK C 工具链（cargo-ndk 可处理） | ~1.5–2 MB | 完整 SQL | 0.40.x |
| JSON 文件 | 零障碍 | ~0 | 无 | — |

## Decision

**采用 `redb` 作为唯一持久化方案，章节索引以「每本书一个序列化 `Vec<Chapter>` blob」的形式存储。**

### 关键论证

**① 本项目没有任何需要 SQL 的查询**

数据模型是五张"单键查值"的表，不存在 JOIN、聚合、范围扫描、事务性多表更新。引入 SQL 引擎是为不存在的能力 paying 成本——包括：Android 交叉编译链上多一个 C 编译环节、APK 大 1.5 MB、构建时间增加约一分钟，以及 Windows 上 MSVC 工具链偶发的链接问题。

**② 章节索引的访问模式与「整体 blob」天然吻合**

打开一本书时，**必然**需要完整章节列表（目录页要展示、跳转要按索引查找、跨章翻页要取下一章）。1000 章的 `Chapter` 结构（约 40 字节/条）序列化后约 40 KB，一次读盘耗时在毫秒级。

对比两种建模：

| 建模 | 打开一本书的成本 |
|---|---|
| 逐章一行 | 1000 次 B+Tree 查找，或一次全表范围扫描 |
| **每书一个 blob** | **1 次读盘 + 1 次反序列化** |

后者不仅更快，而且**语义上更准确**——章节索引是一个不可分割的整体（切章算法一变，整本索引同时失效），本就不该被拆成可独立更新的行。

**③ 与「永不整书入内存」原则不冲突**

这里入内存的只是**索引**（几十 KB），不是正文。正文按 `Chapter.start..end` 字节区间从 `content.txt` 按需读取，通常每章 3–10 KB。

**④ 纯 Rust 在移动端交叉编译上的价值被反复验证**

`rusqlite` 的 `bundled` 特性需要 libsqlite3-sys 用 NDK 的 clang 编译 C 代码。虽然 `cargo-ndk` 能处理，但这是构建链上一个额外的失败点，尤其在多 ABI、CI 与本地环境不一致时容易出问题。纯 Rust 依赖把这个变量消掉了。

### 被排除的方案

| 方案 | 排除理由 |
|---|---|
| **rusqlite (bundled)** | 功能过剩。**切换触发条件**：将来需要跨书全文检索、阅读统计报表、或希望外部工具直接读库时，应重新评估——届时用 SQL 的收益会超过交叉编译的成本 |
| **纯 JSON 文件** | 缺少并发安全与原子写保证；进度这种高频写入用"整文件重写"代价过高且易损坏 |
| **sled** | 项目维护活跃度不及 redb，且 API 承诺为 beta |

## Consequences

### 变得更简单

- 依赖树完全无 C 代码，`cargo ndk` 一次通过
- APK 体积比 SQLite 方案小约 1.5 MB
- 序列化用 `postcard`，紧凑且零拷贝友好
- 单文件数据库，备份与调试都是"拷一个文件"

### 变得更困难

- 没有 SQL，所有查询需要手写索引（例如"按 `last_read_at` 排序的书架列表"需要在内存中排序，或用维护好的二级索引）
  - **缓解**：书库量级是数百本，内存排序成本可忽略
- Schema 演进需要手写迁移逻辑（redb 无 `ALTER TABLE`）
  - **缓解**：在 value 里加版本号前缀，读取时按版本分支处理
- 缺少成熟的 GUI 查看工具
  - **缓解**：`books/<id>/meta.json` 保留一份人类可读的冗余副本

### 具体的表设计

| 表 | Key | Value | 说明 |
|---|---|---|---|
| `books` | `BookId` (16 B) | `Book` (postcard) | 书架列表 |
| `chapters` | `BookId` (16 B) | `Vec<Chapter>` (postcard) | 整块 |
| `progress` | `BookId` | `ReadingProgress` | 高频写，防抖落盘 |
| `bookmarks` | `Uuid` (16 B) | `Bookmark` | |
| `bm_by_book` | `(BookId, Uuid)` (32 B) | `()` | 二级索引，按书列书签 |
| `settings` | `&str` | `postcard` | 全局 + 每书覆盖 |

### 写入策略

| 数据 | 策略 |
|---|---|
| 进度 | 3 秒防抖；`onPause` / 切换书籍 / 退出应用时**立即强制落盘** |
| 书签、设置 | 即时落盘 |
| 分页缓存 | 可重建，写入失败静默降级为内存缓存 |
| 正文 `content.txt` | 导入时一次写入，此后只读 |

### 需要长期留意的风险

- `/data/data/<pkg>/files/` 在卸载应用时会被系统删除。1.0 定位为"本地阅读器"，不做云备份，因此**卸载即丢失书库与进度**，这一点需要在产品说明中明确告知用户。
