# ADR-003: 采用 Tauri 2 作为跨端外壳

## Status

**Accepted** —— **Supersedes [ADR-001](ADR-001-UI与渲染技术路线.md)**

## Context

[ADR-001](ADR-001-UI与渲染技术路线.md) 最初选定 `egui + cosmic-text`，并列出了四条理由。随后项目 owner 提出质疑（「前端可以用 CSS，Tauri 2 有其他不行的理由吗？」），触发了一次全面复议。复核结果确认原论证存在**两处判断偏差**（完整记录见 ADR-001 的「复议记录」章节）：

| 原论证 | 复核结论 |
|---|---|
| 「排版靠 CSS」控制力不足 | ❌ **错误**。对中英混排的中文阅读器，浏览器排版引擎反而更强（禁则内置、字体回退全自动、标点挤压与中西文间距原生支持、竖排直接可用） |
| 「WebView 的内存与启动开销不符合纯净轻量定位」 | ⚠️ **证据不足**。实测约 300 ms 冷启动、约 110 MB 常驻内存，都不构成障碍；真实差异只是相对自绘路线多约 50–70 MB |
| 附带的：egui 侧「中文禁则需自研」（原 R1，概率评级"高"） | ⚠️ **高估**。`cosmic-text` 基于 UAX #14，而 UAX #14 已规定 CJK 禁则。**基础禁则在两条路线上都免费**，因此排版质量**不构成区分度** |

复议得出的关键结论是：**真正的问题不是"Tauri 行不行"，而是这个项目更看重什么。**

项目 owner 随后明确了首要约束：

> 「我更偏向于使用 Tauri 2，因为我对应 UI 美观度层面有很高的要求，既然我们做了，就必须得做的好看且好用。」

**即：UI 美观度被确立为项目的首要质量属性。**

## Decision

**采用 Tauri 2 作为跨端外壳，UI 层使用 Web 技术栈（HTML/CSS/TS），Rust 保留为内核。**

这个决策同时改变了三件事：

| 项 | 原方案（ADR-001） | 现方案（ADR-003） |
|---|---|---|
| UI 层实现语言 | Rust（egui 自绘） | HTML / CSS / TypeScript |
| 排版与分页 | 自研（cosmic-text + 自定义分页引擎 + 字形图集） | **交给 WebView 排版引擎** |
| 工程链 | 纯 Cargo workspace | Cargo（内核）+ Node/Vite（前端）双工具链 |

**明确保留不动的部分**：`reader-core`（领域模型、编码识别、文本规范化、章节切分、redb 存储、导入管线）**完全复用，一行不改**。

## Consequences

### 变得更简单

| 收益 | 说明 |
|---|---|
| **视觉表现力** | CSS 提供的能力集远超自绘：过渡动画、滤镜、阴影、圆角、毛玻璃、`transform` 3D 翻页。这是本决策的核心动机 |
| **CJK 排版开箱即得** | 断行禁则由引擎内置；字体回退（生僻字、繁体、emoji）全自动，无需 `fontdb` 与字体链维护 |
| **进阶排版特性免费** | `text-spacing-trim`（标点挤压，Chrome 123+）、`text-autospace`（中西文间距，Chrome 120+）、`writing-mode: vertical-rl`（竖排）——这些在原方案里都要自研或做不了 |
| **安全区适配大幅简化** | CSS `env(safe-area-inset-*)` 一行解决，无需手写 window insets 计算（原方案的 R2 风险几乎消失） |
| **样式迭代速度** | 改 CSS 所见即所得，比改自绘代码快一个数量级 |
| **主题系统** | CSS 变量即可实现白/纸黄/夜间，且可做平滑过渡 |
| **同引擎覆盖两个目标平台** | Windows 用 WebView2、安卓用系统 WebView，**都是 Chromium**，不存在跨引擎行为差异 |

### 变得更复杂

| 代价 | 说明 | 缓解 |
|---|---|---|
| **引入第二语言与 Node 工具链** | 需要维护 Rust 与 TS 两套代码与心智 | 用 `tauri-specta` 从 Rust 类型**自动生成** TS 类型与调用封装，消除契约漂移 |
| **IPC 契约成为新的核心设计点** | 取代了原来的"分页引擎"成为最需要精心设计的部分 | 采用**粗粒度命令**设计（一次调用返回整章，而非高频小调用）；见架构文档 §4 |
| **WebView 版本碎片化** | 老设备的系统 WebView 可能长期未更新，`text-spacing-trim` 等新特性拿不到 | 构建层降级 target（如 `chrome90`）；新特性作为**渐进增强**而非必需依赖 |
| **移动端生态相对薄** | 冷门原生能力需要自己写插件 | 1.0 所需能力（文件选择、全屏、常亮）都有现成方案或 Web API |
| **内存占用上升** | 约 110 MB vs 自绘路线 50 MB 量级 | 接受。仅对 2–3 GB 低端机有实际影响 |
| **跨设备排版结果不可复现** | 由引擎决定，无法像纯函数那样快照测试 | 排版正确性由引擎保证；我们的测试重点转向**进度锚点与数据管线** |

### 被废弃的原方案组件

以下在原设计中占据大量工作量的模块，**在新方案中不再需要**：

- ❌ `infra/paginate.rs` 分页引擎（纯函数）
- ❌ `infra/layout_cache.rs` 分页缓存
- ❌ `reader-ui` 字形图集（`SwashCache` → `TextureHandle`）
- ❌ `fontdb` 系统字体扫描与字体链维护
- ❌ `reader-ui` 全部 egui 组件与自绘手势

### 保留的资产

以下在两条路线上完全一致，**不受本次决策影响**（这也是分层架构的直接回报）：

- ✅ `reader-core::domain` —— `Book` / `Chapter` / `ReadingProgress` / `Bookmark` / `ReaderSettings`
- ✅ `reader-core::infra::encoding` —— 编码识别
- ✅ `reader-core::infra::normalize` —— 文本规范化
- ✅ `reader-core::infra::chapterize` —— 章节切分
- ✅ `reader-core::infra::repo` —— redb 仓储
- ✅ `reader-core::infra::textfile` —— 按字节区间读取单章
- ✅ 两条关键不变式（不丢字、进度往返）的**语义**
