# 01 · 可行性分析

> 评估对象：用 Rust 开发一个跨端（Windows 桌面 + 安卓手机 + 安卓平板）的纯净版 TXT 小说阅读器。
> 评估基准时间：**2026-10**，所有版本号均为该时间点的实际可用版本。

> ## ⚠️ 阅读须知
> 本文是 **2026-10-09 的初版分析**，结论为「选 egui」。该结论**已于同日被 [ADR-003](adr/ADR-003-采用Tauri2作为跨端外壳.md) 推翻**，项目最终采用 **Tauri 2**。
> 本文**完整保留**作为决策留痕。其中 §2.1 的「复议记录」章节记录了初版的两处判断偏差与修正过程；**当前有效的架构请以 [02-架构设计.md](02-架构设计.md) 与 [ADR-003](adr/ADR-003-采用Tauri2作为跨端外壳.md) 为准。**

## 1. 范围界定

先把 1.0 的边界钉死。范围蔓延是这类个人项目最常见的死因。

### 1.0 做（In Scope）

| 能力 | 说明 | 必要性 |
|---|---|---|
| TXT 导入 | 本地文件导入，自动识别编码（UTF-8 / UTF-16 / GBK / GB18030 / Big5 等） | 核心 |
| 章节切分 | 按「第 X 章 / 回 / 节 / 卷」正则自动切章；切不出章节时降级为按字数均分 | 核心 |
| 书架 | 列表 / 网格展示、封面占位、最近阅读排序、删除、重命名 | 核心 |
| 阅读排版 | 字号、行距、字体、页边距、首行缩进、换行规则 | 核心 |
| 翻页 | 点击分区翻页 + 左右滑动翻页 | 核心 |
| 主题 | 白 / 纸黄 / 夜间 三套 | 核心 |
| 阅读进度 | 自动保存与恢复，精确到章节 + 页内偏移 | 核心 |
| 目录 | 章节列表跳转 | 核心 |
| 书签 | 添加 / 删除 / 跳转 | 核心 |
| 沉浸模式 | 全屏、隐藏状态栏、点击中央呼出菜单 | 核心 |
| 平板适配 | 按窗口尺寸切换单栏 / 双栏与页边距 | 核心 |

### 1.0 不做（Out of Scope）

| 不做的事 | 原因 |
|---|---|
| EPUB / MOBI / PDF / AZW3 | 解析复杂度是 TXT 的 5–10 倍，留到 2.0 |
| TTS 朗读 | 涉及平台原生语音 API 与音频线程，独立课题 |
| 云同步 / 账号 | 直接违背「无网络」约束 |
| 在线书城 / 网络小说抓取 | 产品方向不同 |
| 笔记 / 批注 / 全文检索 | 1.0 保持单一目标 |
| iOS | 无 Mac 构建机；架构上预留但不投入 |
| 仿真翻页（卷页动画） | 视觉效果成本极高，1.0 用平移 / 淡入代替 |

## 2. 技术选型

### 2.1 UI 框架 —— 最关键的一次决策

这是整个项目**唯一一个选错了就要推倒重来**的决策，因此单独出 ADR。此处只给对比结论。

| 框架 | 版本<br>(2026-10) | 许可 | 安卓官方支持 | 渲染方式 | 排版控制力 | 移动端成熟度 |
|---|---|---|---|---|---|---|
| **egui / eframe** | 0.36.1 | MIT OR Apache-2.0 | ✅ 官方<br>(android-activity) | 自绘 | ★★★★★ | ★★★☆ |
| **Slint** | 1.17 | GPLv3 / Royalty-Free<br>(需署名) / 商业 | ✅ 官方 | 自绘(Skia/WGPU/软件) | ★★★☆ | ★★★★★ |
| **Dioxus** | 0.7 | MIT OR Apache-2.0 | ⚠️ 支持但原生渲染器仍实验性 | WebView 或实验性 WGPU | ★★ | ★★☆ |
| **Tauri 2** | 2.x | MIT OR Apache-2.0 | ✅ 官方 | 系统 WebView | ★★★<br>(靠 CSS) | ★★★★ |

**结论（初版）：选 egui + eframe。**

> ⚠️ **此结论已被 [ADR-003](adr/ADR-003-采用Tauri2作为跨端外壳.md) 推翻**。项目 owner 随后将「UI 美观度」确立为首要质量属性，最终改选 **Tauri 2**。
> 以下原论证**完整保留**，作为决策留痕；其中的判断偏差见本节末尾的「复议记录」。

**理由（按权重排序）**

1. **许可零摩擦**：MIT OR Apache-2.0，不引入任何署名义务或商业授权闸门。Slint 的 Royalty-Free 许可虽然桌面/移动免费，但要求保留「Made with Slint」署名，且是两选一还是三选一的授权结构会给未来留不确定性。
2. **排版控制力最高**：阅读器的成败在排版细节。egui 是立即模式 + 全自绘，意味着**每一个像素都由我们决定**——行距、字距、页边距、标点处理都不受框架内置组件约束。Slint 的 `Flickable` / `ListView` 让我们少写滚动代码，但也意味着排版细节要跟框架博弈。
3. **「立即模式不适合长列表」的缺点在本项目不成立**：因为阅读器天然采用**分页模型**而非无限滚动模型。一页几百个字，重绘成本可以忽略；静止时通过 `request_repaint_after` 进入空闲，不烧电。
4. **生态体量**：egui 是 Rust GUI 里社区最大的（周下载量、示例数、第三方组件），遇到问题更容易搜到答案。0.36.1 于 2026-08 发布，修复了移动端 IME、拖拽等一堆交互问题，正处于活跃上升期。

**明确接受的代价**

| 代价 | 说明 | 缓解 |
|---|---|---|
| 安全区 / 刘海适配要手写 | egui 的安卓后端不自动处理 status bar / 挖孔屏 inset | M4 阶段用 `android-activity` 暴露的 window insets 计算页面内边距 |
| 软键盘弹起需自行避让 | 1.0 只在一处用到输入法（搜索框，且属 2.0） | 降低优先级，1.0 基本不触发 |
| 需自建文件选择桥 | egui 不含文件对话框 | 见 2.4 |
| 无声明式布局 DSL | UI 代码是 Rust 函数 | 对单人项目反而减少了一层概念 |

> 如果后续更看重「移动端适配少写代码」，切换到 Slint 的主要改动集中在 `reader-ui` 与 `app-android` 两个 crate，`reader-core` 与排版引擎可原样保留——这是分层设计的价值所在。

> **复议记录（2026-10-09）**：初版把 Tauri 的「排版靠 CSS」当作缺点，**这个判断是错的**——对中英混排的中文阅读器，浏览器排版引擎反而更强。
> 同时初版把「中文禁则需自研」列为高概率风险，也是**高估**：UAX #14 本身已规定 CJK 禁则，cosmic-text 与浏览器都免费获得。
> 修正后的完整对比与仍然成立的理由，见 [ADR-001 §复议记录](adr/ADR-001-UI与渲染技术路线.md)。

### 2.2 排版与渲染内核

| 方案 | 说明 | 判词 |
|---|---|---|
| **cosmic-text** | 纯 Rust。harfrust 整形、Unicode BiDi、字体回退（复用 Chromium/Firefox 回退表）、命中测试、逐行布局缓存、swash 字形光栅化。MIT/Apache | ✅ **推荐** |
| egui 内置 Galley（epaint） | 零额外依赖，但首行缩进、标点禁则等粒度不够，且布局结果不易脱离 GPU 单测 | 备选 |
| 自研排版 | 中文无连字、无上下文变形 | ❌ 不必要的重造轮子 |

**一条重要的技术判断**：中文排版的技术难点**不在"文本整形"**（汉字没有连字和上下文变形，逐字等宽推进即可），**而在"断行规则"**。所以：

- cosmic-text 直接解决约 **80%** 的问题（整形、布局、字体回退、缓存、命中测试）；
- 剩下约 **20%** —— **标点禁则（避头尾）与标点挤压** —— 任何现成库都不会替我们决定，必须自研一张规则表（详见架构文档 §6）。

**关键收益**：cosmic-text 是**与 UI 框架无关**的。把分页引擎写成 `(章节文本, 排版参数, 视口尺寸) → 页边界数组` 的**纯函数**，就可以在没有 GPU、没有窗口的环境下跑单元测试。这是本项目可维护性的核心保障。

### 2.3 本地存储

| 方案 | 版本 | 交叉编译 | 体积增量 | 查询能力 | 判词 |
|---|---|---|---|---|---|
| **redb** | 2.6.3 | ✅ 零障碍（纯 Rust） | ~200–300 KB | KV / B+Tree | ✅ **推荐** |
| rusqlite (bundled) | 0.40.x | ⚠️ 需 NDK C 工具链（cargo-ndk 可处理） | ~1.5–2 MB | 完整 SQL | 备选 |

**结论：redb。**

理由：本项目数据模型极其简单（书 / 章节索引 / 进度 / 书签 / 设置），**没有任何需要 JOIN 或聚合的查询**；章节索引天然适合"每本书一个序列化 blob，一次读取"，这比 SQL 表更贴合访问模式。用 redb 换掉的是：Android 交叉编译链里少一个 C 编译环节、APK 小 1.5 MB、编译快一分钟。

**切换到 SQLite 的触发条件**：将来要做跨书全文检索、阅读统计、或者需要外部工具直接读库。

### 2.4 文件导入（跨端，历史上最大的坑）

| 平台 | 方案 | 说明 |
|---|---|---|
| Windows / macOS / Linux | **rfd 0.17** | 系统原生文件对话框，成熟稳定（月下载 350 万+） |
| Android | **robius-file-picker 0.3.1** | 走系统文档选择器（`ACTION_OPEN_DOCUMENT`），把 `content://` URI 自动流式复制到应用缓存目录，直接给出可用路径。minSdk 26 |
| Android（兜底） | 自写 Kotlin 桥（约 100 行） | `registerForActivityResult(ActivityResultContracts.OpenDocument())` + JNI 回传路径 |
| Android（补充入口） | `text/plain` intent-filter | 用户在文件管理器里「打开方式 → 本应用」，零权限焦虑、零弹窗，体验最好 |

**这是本次评估中最值得高兴的发现**：过去「Rust 做安卓 GUI 必须自己写 Kotlin 文件选择」的痛点已有现成 crate 覆盖，风险从「高」降为「中低」。

**存储策略（规避 Android 分区存储争议）**：
> 导入后**立即把文件内容复制进应用私有目录**（`/data/data/<pkg>/files/books/`），此后只读私有副本。这样：
> - 不需要 `MANAGE_EXTERNAL_STORAGE`（会被应用商店拒审）
> - 不需要持久化 URI 授权
> - 用户删掉原始文件、拔掉 SD 卡都不影响阅读

### 2.5 构建与打包

| 目标 | 工具链 | 关键参数 |
|---|---|---|
| Windows | `cargo build --release` | 产物 `.exe`；如需安装包可加 cargo-wix |
| Android | `cargo-ndk` + Gradle | 见下 |

**Android 交叉编译要点**

- Rust target 与 Android ABI 的对应关系（名字不一致，容易踩）：

| Rust target | Android ABI | 用途 |
|---|---|---|
| `aarch64-linux-android` | `arm64-v8a` | 现代真机（**必编**） |
| `armv7-linux-androideabi` | `armeabi-v7a` | 老 32 位设备（可选） |
| `x86_64-linux-android` | `x86_64` | 模拟器（开发期必编） |

- NDK 版本必须**钉死**（推荐 r27/r28 系列），否则不同机器链接行为不一致。
- `minSdk = 26`（Android 8.0）：覆盖面已足够广，且能直接用 `InMemoryDexClassLoader` 等 API。
- 渲染后端优先 **glow（OpenGL ES 3.0）** 而非 wgpu：老设备 Vulkan 支持不全，GLES 兼容性更稳。
- Activity 类型选 **GameActivity** 而非 NativeActivity：输入与 IME 支持更好。
- ABI 数量直接决定 APK 体积，建议 `arm64-v8a` + `x86_64` 起步，上架前再补 `armeabi-v7a`。

## 3. 可行性结论

### ✅ 判定：可行

逐条对照 1.0 的核心能力需求，**没有一项缺位**：

| 需求 | 支撑方案 | 成熟度 |
|---|---|---|
| 跨端 UI（桌面+安卓） | ~~egui + eframe~~ → **Tauri 2**（已被 ADR-003 取代） | 成熟 |
| 中文文本排版 | cosmic-text（含 CJK 截图验证） | 成熟 |
| 中文编码识别 | chardetng + encoding_rs（Firefox 同源） | 成熟 |
| 安卓文件导入 | robius-file-picker（走 SAF） | 新但专用 |
| 本地持久化 | redb | 稳定版 1.0+ |
| 跨平台系统字体加载 | fontdb 扫描系统字体目录 | 成熟 |
| 安卓打包 | cargo-ndk + Gradle | 成熟 |

### ⚠️ 三个真实的不确定性（不粉饰）

1. **中文标点禁则没有现成 Rust 库** —— 必须自己写规则表。这不是"能不能做"的问题，而是"做得够不够细"的问题。行首不能出现 `，。！？、；：）》」』】`，行尾不能出现 `（《「『【`。约 30 条规则 + 标点挤压策略，可控但需要打磨。
2. **中文字体不能随包分发** —— 思源黑体/宋体单字重 10 MB+，多重字重会让 APK 膨胀到不可接受，且有授权问题。**方案：运行时加载系统字体**（安卓自带 Noto Sans CJK，Windows 用微软雅黑，需要时允许用户导入字体文件）。这带来一个副作用：**不同设备字体不同 → 分页结果不同**，所以分页缓存必须以「字体 + 字号 + 视口」为 key（架构已考虑）。
3. **egui 移动端仍在演进** —— 0.36 才显著改善 IME。若 1.0 意外需要复杂文本输入，可能撞上坑。缓解：把输入法相关功能全部推后。

## 4. 风险矩阵

按「概率 × 影响」排序。**影响 = 对 1.0 交付的威胁程度**。

| # | 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|---|
| R1 | 标点挤压与更精细的禁则需自研（**基础禁则由 UAX #14 覆盖，已下调评级**） | 中 | 中 | 规则表外置为数据；用固定语料做快照测试；1.0 只做基础禁则，标点挤压推迟。见 §2.1 复议记录 |
| R2 | 安卓安全区 / 状态栏遮挡，需大量试错 | 高 | 中 | M4 专项处理；准备真机 + 模拟器双验证；页面内边距做成可配置常量 |
| R3 | Android 交叉编译环境搭建反复失败 | 中 | 中 | 环境脚本化 + 钉死 NDK 版本；尽早（M0 后）跑通一次 "Hello World APK" 打穿链路 |
| R4 | 大文件（10 MB+ 长篇）首次打开卡顿 | 中 | 高 | 章节级按需读取，绝不整书入内存；导入阶段一次性完成编码转换与索引，打开时零解码 |
| R5 | 立即模式持续重绘导致耗电 | 中 | 中 | `request_repaint_after` 空闲降帧；静止时不请求重绘 |
| R6 | 系统字体差异导致分页结果漂移 | 中 | 中 | 分页缓存 key 包含字体指纹 + 字号 + 视口尺寸；进度用「章节 + 字符偏移」而非页码 |
| R7 | 框架 API 变动（egui/cosmic-text 迭代快） | 中 | 中 | 锁定小版本（`=0.36`）；排版内核与 UI 解耦，UI 层可替换 |
| R8 | APK 体积过大 | 低 | 低 | release profile 开 LTO + strip + `opt-level="z"`；只编必要 ABI |
| R9 | robius-file-picker 与 egui/android-activity 集成不畅 | 中 | 低 | 已备兜底：自写约 100 行 Kotlin SAF 桥，接口不变 |

## 5. 工作量粗估

单人开发，**纯编码时间**，不含需求反复。两列分别是全职投入与业余投入（每天 2 小时量级）的粗估。

| 阶段 | 内容 | 全职 | 业余 |
|---|---|---|---|
| M0 | 工程骨架：workspace、core 领域模型、redb 仓储、桌面空窗口打穿 | 2 d | 4 d |
| M1 | 导入管线 + 书架：编码识别、切章、落盘、书库列表 | 5 d | 10 d |
| M2 | 排版内核：cosmic-text 分页引擎 + 字形渲染 + 字号/行距/主题 + 进度保存 | 6 d | 12 d |
| M3 | 阅读体验：翻页交互、目录、书签、设置页、沉浸模式 | 6 d | 12 d |
| M4 | 安卓落地：交叉编译链、SAF 导入、安全区、常亮、图标签名、真机跑通 | 5 d | 10 d |
| M5 | 打磨：大书性能、错误处理、平板双栏、边缘 case | 4 d | 8 d |
| **合计** | | **≈ 28 个全职日** | **≈ 56 个业余日** |

**风险缓冲建议**：在合计之上留 **30% 缓冲**用于 R1/R2 的返工。

**最该先做的事**：M0 结束时**就先打穿一次安卓构建链**（哪怕界面只有一个空窗口）。理由——安卓交叉编译是唯一一个"环境问题可能在几天内都定位不到"的环节，把它提前，风险前置暴露。
