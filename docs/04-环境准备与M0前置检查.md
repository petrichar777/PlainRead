## 三、安卓端：需要手动安装

以下步骤**必须由本机所有者操作**（涉及 GUI 安装程序与授权确认），无法自动完成。

### 3.1 安装 Android Studio

下载安装后首次启动会引导安装 SDK。也可只装 Command-line Tools，但 Android Studio 更省事。

### 3.2 通过 SDK Manager 安装组件

| 组件 | 建议版本 | 说明 |
|---|---|---|
| Android SDK Platform | **35** | 对应 `targetSdk = 35` |
| Android SDK Build-Tools | 最新 | |
| **NDK (Side by side)** | **27.2.x（钉死一个具体版本）** | ★ 不同 NDK 版本的链接行为不一致，团队与 CI 必须统一 |
| Android SDK Platform-Tools | 最新 | 提供 `adb` |
| Android SDK Command-line Tools | 最新 | 提供 `sdkmanager` |
| Android Emulator + 系统镜像 | API 35 / `x86_64` | 仅在用模拟器时需要 |

### 3.3 配置环境变量

```bash
export ANDROID_HOME="$LOCALAPPDATA/Android/Sdk"
export ANDROID_NDK_HOME="$ANDROID_HOME/ndk/27.2.<具体版本号>"
export PATH="$PATH:$ANDROID_HOME/platform-tools:$ANDROID_HOME/cmdline-tools/latest/bin"
```

> Windows 上建议写入**系统环境变量**，而不是只写在某个 shell 配置里——否则从 IDE 或 Tauri CLI 启动时可能读不到。

### 3.4 添加 Rust 交叉编译目标

```bash
rustup target add aarch64-linux-android x86_64-linux-android
```

| target | Android ABI | 用途 |
|---|---|---|
| `aarch64-linux-android` | `arm64-v8a` | 现代真机（**必装**） |
| `x86_64-linux-android` | `x86_64` | 模拟器（开发期必装） |
| `armv7-linux-androideabi` | `armeabi-v7a` | 老 32 位设备（上架前再加） |

### 3.5 不需要装的东西（避免浪费时间）

| 组件 | 为什么不需要 |
|---|---|
| `cargo-ndk` | Tauri 2 的 Android 构建链会自行配置 NDK 工具链，无需手动管理 |
| `gradle`（独立安装） | Tauri 生成的工程自带 Gradle Wrapper（`gradlew`） |
| `cargo-apk` | 已被 Tauri CLI 取代 |
| `cargo install tauri-cli` | 改用 npm 安装 `@tauri-apps/cli` 更快（有预编译二进制，省掉数分钟编译） |

| 方案 | 说明 | 优劣 |
|---|---|---|
| **A. 桌面优先（推荐）** | 立即开始 M0 的桌面部分（工程骨架 + IPC 链路打通），安卓环境在方便时安装，装好后立刻补 `android init` 与空壳 APK | M0 的核心目标是**验证 IPC 契约链路**，这与平台无关。桌面先跑通能更早拿到反馈 |

## 六、M0 实测发现的坑（务必记录）

### 6.1 首次编译极慢（★ 已定位并修复）

**当时的实测**

| 项目 | 实测 |
|---|---|
| `reader-core`（约 20 个 crate） | 约 6 分钟 |
| `src-tauri`（完整 Tauri 依赖树，约 400 个 crate） | **约 39 分钟**（首次） |
| `cargo clippy --all-targets`（首次） | 约 35 分钟 |
| 改一行 Rust 后重新链接 | 约 5–6 分钟 |

**当时**归因为"本机编译吞吐偏低（可能是磁盘或杀毒软件扫描）"——**这个归因只对了一半**。

**真正的原因（2026-10-11 查清）**

工程当时放在 `E:` 上，而 `E:` 是**可移动驱动器**（U 盘，卷标 `thinkplus`），
文件系统是 **FAT32**。两条独立的问题叠加：

1. **磁盘慢**：顺序写 20.4 MB/s vs C: 固定盘 1140 MB/s（56×）；小文件写 6.5 MB/s（17×）；
2. **FAT32 不支持硬链接** → cargo 增量缓存退化为逐文件复制
   （日志里那句 `hard linking files in the incremental compilation cache failed` 就是它）。

**处理**：工程已迁到固定盘 `C:\项目\简阅`，并引入 Cargo workspace。
完整论证、实测数据与两条连带约定见 **[ADR-005](adr/ADR-005-采用Cargo工作区与工程落盘固定盘.md)**。

> 教训：**"机器慢"要先量化再下结论。** 一次 `fsutil fsinfo drivetype` +
> 两个盘的读写基准，十分钟就能把"玄学慢"变成"U 盘 + FAT32"这个确定结论。
> 顺带一提，"某个操作慢"的归因里，"存储介质"这一项值得**优先**排查——
> 它比 CPU/内存更容易被忽略，而影响往往大一个数量级。

### 6.2 `indexmap` 探测失败导致 Tauri 编译中断

**症状**

```
error[E0107]: struct takes 3 generic arguments but 2 generic arguments were supplied
  --> schemars-0.8.22/src/lib.rs:12:32
12 | pub type Map<K, V> = indexmap::IndexMap<K, V>;
   note: struct defined here, with 3 generic parameters: `K`, `V`, `S`
  --> indexmap-1.9.3/src/map.rs:76:12
```

出错点在 `tauri-build → schemars 0.8.22`，**不是我们的代码**。

**根因**

`indexmap 1.9.3` 的 `[features]` 里**没有 `default`**，因此 `std` 默认关闭。它在这种情况下的 build.rs 会走真实探测分支：

```rust
match std::env::var_os("CARGO_FEATURE_STD") {
    Some(_) => autocfg::emit("has_std"),
    None    => autocfg::new().emit_sysroot_crate("std"),  // ← 会 spawn rustc 探测
}
```

探测失败（受限构建环境 / CI 沙箱 / 子进程受限）时 `has_std` 不会被 emit，于是
`map.rs` 里的 `IndexMap<K, V, S = RandomState>` 退化为三泛型版本 `IndexMap<K, V, S>`，
`schemars 0.8.22` 的 `Map<K, V>` 别名立刻编译失败。

**修复**（已写入 `src-tauri/Cargo.toml`）

```toml
# 显式启用 std，让 indexmap 走 emit("has_std") 分支，绕开运行时探测
indexmap = { version = "1.9", features = ["std"] }
```

**为什么这个修复是值得保留的（而不是一次性 hack）**

它把"能不能编译通过"从一个**环境依赖的不确定问题**，变成了**确定性问题**。
代价只是多一条不直接使用的依赖。收益是构建在本地、CI、别的机器上表现一致。

> 教训：这类"某个 crate 的 build.rs 会 spawn 子进程做探测"的依赖，
> 在受限构建环境里都可能突然失效。以后遇到类似症状（本地能编、CI 不能编，
> 或反之），优先怀疑 build script 的探测逻辑。

### 6.3 `cargo test` 在 Windows 上启动即崩（`0xc0000139`）

**症状**

`cargo test` 能编译通过，但测试二进制**在执行任何 Rust 代码之前就退出**：

```
error: test failed, to rerun pass `--lib`
Caused by:
  process didn't exit successfully: `...\plainread_lib-<hash>.exe`
  (exit code: 0xc0000139, STATUS_ENTRYPOINT_NOT_FOUND)
```

一条测试都跑不到。连带后果：`export_bindings()` 执行不到 →
`src/ipc/bindings.ts` 永远生成不出来 → 前端 `tsc` 直接报模块不存在。

**根因**

Tauri 依赖树里的 `tao` / `muda` 静态导入 `comctl32.dll` 里 **Common Controls v6 专有**的入口点
（`TaskDialogIndirect` 等）。要加载到 v6，可执行文件必须带一份声明了 v6 依赖的应用清单。

而 `tauri_build::build()` 生成的清单**只发给 bin 目标**：

```
cargo:rustc-link-arg-bins=<OUT_DIR>/resource.lib      ← 只有这一条
```

测试目标拿不到清单，Windows 便退回 System32 里的 comctl32 **v5.82**，
导入表里的 v6 入口点解析失败 → 加载阶段终止。

**修复**（已写入 `src-tauri/build.rs`）

对 msvc 目标发延迟加载指令，**全目标生效**：

```rust
println!("cargo:rustc-link-arg=/DELAYLOAD:comctl32.dll");
println!("cargo:rustc-link-arg=delayimp.lib");
```

| 目标 | 效果 |
|---|---|
| 测试二进制 | 单元测试不会调用那些 GUI 函数 → 永不解析 → 正常启动 |
| 主程序 | 带 v6 清单，SxS 照常解析到 comctl32 v6，对话框行为不变 |

**为什么不用「给测试也补一份清单」**

Cargo **没有**「只针对单元测试二进制」的链接指令：

| 指令 | 实际作用范围 |
|---|---|
| `cargo:rustc-link-arg-tests` | **仅 `tests/` 目录下的集成测试**，覆盖不到 lib 内 `#[cfg(test)]` 的单元测试 |
| `cargo:rustc-link-arg` | 全部可链接目标 —— 但会给 bin 塞第二份清单资源，有 `CVTRES: duplicate resource` 风险 |

> 教训：`rustc-link-arg-tests` 的名字有误导性，它**不是**「所有测试目标」。
> 另外，这一类问题的诊断捷径是对比实验：本项目 `cargo test -p reader-core`
> （纯 Rust、不依赖 Tauri）全部通过，一步就把嫌疑范围从"环境问题"缩小到"Tauri 栈特有的链接问题"。

### 6.4 specta 拒绝导出 `i64`，导致整个前端编不过

**症状**

测试能跑了，但契约导出这一步失败：

```
Attempted to export "plainread_lib::ipc::dto::BookSummary.lastReadAt"
but Specta forbids exporting BigInt-style types (usize, isize, i64, u64, i128, u128)
to avoid precision loss.
```

**根因**

JS 的 `number` 是 f64，超过 2^53 的整数会被 `JSON.parse` 静默截断。
specta 因此**默认禁止**导出这些类型——它宁可让构建失败，也不愿在运行时悄悄丢精度。

**修复**（已写入 `src-tauri/src/ipc/dto.rs`）

一次字段一个覆盖，显式接受 f64 语义：

```rust
#[specta(type = Option<specta_typescript::Number>)]
pub last_read_at: Option<i64>,
```

毫秒时间戳当前约 `1.8e12`，距 2^53（约 `9.0e15`）有三个数量级余量，映射成 `number` 是无损的。

**为什么逐字段写，而不是全局放行**

specta 还提供全局 `Remapper` 把 `i64/u64/usize` 一律重映射为 `number`（官方标注为 *highly not recommended*）。
本项目**不用**它：逐字段覆盖让这个决定**在它发生的那个字段上可见**。
将来若真的出现需要完整 64 位精度的字段（例如内容哈希），它会因为缺少这行覆盖而在构建期报错，
被迫显式决策 —— 而不是被一条全局规则悄悄降级成 f64。

**为什么这是 M0 该暴露的问题**

契约是前端编译的硬依赖。这类问题若拖到 M1（开始加真实 DTO 字段时）才发现，
会一次性积累出好几个字段要改。M0 用一个字段就把边界情况逼出来了。

**附带发现（specta 的小怪癖）**

`f32` / `f64` 会导出成 `number | null` —— 因为 specta 认为浮点可能是 `NaN` / `Infinity`，
而 JSON 会把它们序列化成 `null`。所以绑定文件里出现
`defaultFontSize: number | null` 是**预期行为**，不是错误。

### 6.5 测试用例之间靠副作用依赖 → 假失败

**症状**

`export_bindings_should_succeed` 通过，但另一个断言「绑定文件存在」的测试报文件不存在——
而文件其实**已经生成好了**。

**根因**

它们本是两个独立的 `#[test]`，而 Rust 测试**默认并行执行**。
「检查文件存在」的测试完全可能抢在「写文件」的测试之前跑完。

**修复**

合并成一个自包含的测试（导出 + 落点校验），不再让测试之间靠副作用互相依赖。

**附带加固**

导出路径由「相对于进程当前目录」改为基于 `CARGO_MANIFEST_DIR` 的绝对路径。
相对路径在 `cargo test` / `tauri dev` / IDE 里跑测试时当前目录并不一致，
一旦对不上，症状就是「导出报告成功，但文件出现在别处」——极难排查。
