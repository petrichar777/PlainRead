## 1. 架构目标与原则

| 目标 | 具体含义 | 为什么对本项目重要 |
|---|---|---|
| **视觉表现优先** | UI 层用 Web 技术，追求精致的排版与动效 | 项目 owner 明确的首要质量属性 |
| **IPC 契约稳定** | Rust 与前端的接口是**粗粒度、强类型、可自动生成**的 | 双语言架构下，契约漂移是最主要的维护风险 |
| **内核与外壳解耦** | `reader-core` 不含任何 Tauri / 前端相关代码 | 保证内核可单测，且前端框架可替换 |
| **平台差异只在一处** | 安卓特有的沉浸、常亮、文件选择收拢到 `platform` 模块 | 不污染业务代码 |
| **大文件永不整书入内存** | 按章节读取，章节索引是唯一全局结构 | 10 MB 长篇 + 中低端安卓机 |
| **进度不因排版变化而丢失** | 进度存「章节 + 字符偏移」，不存页码 / 滚动百分比 | 换字号、换字体、换设备后仍回到同一句话 |

### 明确拒绝的做法（反过度设计）

- ❌ 不引入全局状态管理库（Redux / Zustand / Jotai）—— 四屏应用的状态量不需要
- ❌ 不用 SSR / SSG 前端框架（Next.js / Nuxt）—— Tauri 是纯静态前端，服务端渲染毫无用处
- ❌ 不做插件化 / 多格式解析器抽象 —— 1.0 只有 TXT
- ❌ 不把 async runtime 引入内核 —— 本地 IO 用 `std::thread` 足够；Tauri 命令本身可为同步函数
- ❌ 不做高频细粒度 IPC —— 一次调用返回一整章，而不是"取一行""取一段"

## 2. 分层架构

```
┌──────────────────────────────────────────────────────────────┐
│  WebView 前端              React + TypeScript + Tailwind      │
│  ─────────────────────────────────────────────────────────── │
│  书架 · 阅读 · 目录 · 设置                                     │
│  ★ 排版、分页、动画、主题全部由浏览器引擎与本层负责               │
└───────────────────────────┬──────────────────────────────────┘
                            │  IPC：命令（前端→Rust）+ 事件（Rust→前端）
                            │  契约见 §4，强类型，自动生成 TS
┌───────────────────────────▼──────────────────────────────────┐
│  Tauri 命令层              src-tauri/src/commands             │
│  唯一对外接口，粗粒度，返回整块数据                              │
├──────────────────────────────────────────────────────────────┤
│  平台适配层                src-tauri/src/platform             │
│  文件选择（SAF / 原生对话框）· 沉浸全屏 · 屏幕常亮               │
├──────────────────────────────────────────────────────────────┤
│  Rust 内核                 crates/reader-core                 │
│  ★ 与 ADR-001 方案完全一致：领域模型 · 编码识别 · 规范化         │
│    · 章节切分 · redb 存储 · 导入管线                           │
└──────────────────────────────────────────────────────────────┘
```

**关键结构性事实**：最下面一层的 `reader-core` 是上一版架构的原样保留。**UI 框架的更换只影响上面三层**，这正是分层设计在此次方向调整中兑现的价值。

## 4. IPC 契约（本方案最核心的设计）

在自绘方案里，最需要打磨的是分页引擎。在 Tauri 方案里，**这个位置被 IPC 契约取代**。

### 4.1 设计原则

| 原则 | 说明 |
|---|---|
| **粗粒度** | 一次调用返回一整章（3–10 KB），而不是逐行或逐段。翻页**不产生任何 IPC**——文本已经在前端了 |
| **强类型且自动生成** | 用 `tauri-specta` 从 Rust 类型生成 TS 类型与调用封装，消除手动同步导致的契约漂移 |
| **错误统一** | 所有命令返回 `Result<T, AppError>`，`AppError` 实现 `Serialize`，前端得到结构化的 `{ code, message }` |
| **后端不持有 UI 状态** | 命令只做"取数据 / 存数据"；当前页码、动画状态等属于前端职责 |

### 4.2 命令清单

| 命令 | 入参 | 返回 | 说明 |
|---|---|---|---|
| `list_books` | — | `Book[]` | 书架列表，按 `last_read_at` 排序 |
| `pick_and_import` | — | `ImportResult` | 调起文件选择 + 导入（桌面原生对话框 / 安卓 SAF） |
| `import_paths` | `paths: string[]` | `ImportResult` | 「打开方式」入口传入时使用 |
| `delete_book` | `bookId` | `void` | 同时清理 redb 记录与 `books/<id>/` 目录 |
| `rename_book` | `bookId, title` | `Book` | |
| `open_book` | `bookId` | `BookSessionDto` | **一次返回**：元信息 + 章节列表 + 上次进度 + 已合并设置 |
| `load_chapter` | `bookId, index` | `ChapterDto` | **一次返回整章文本** |
| `save_progress` | `bookId, chapterIndex, charOffset` | `void` | 前端防抖调用，Rust 侧再防抖落盘 |
| `list_bookmarks` | `bookId` | `Bookmark[]` | |
| `add_bookmark` | `bookId, chapterIndex, charOffset, excerpt` | `Bookmark` | |
| `remove_bookmark` | `bookmarkId` | `void` | |
| `get_settings` | — | `ReaderSettings` | 全局默认 |
| `save_settings` | `settings` | `void` | |

`BookSessionDto` 的字段设计（体现"粗粒度"）：

```rust
#[derive(Serialize, Type)]
pub struct BookSessionDto {
    pub book: Book,
    pub chapters: Vec<Chapter>,        // 整本索引，一次给全
    pub progress: Option<ReadingProgress>,
    pub settings: ReaderSettings,      // 已合并「全局默认 + 每书覆盖」
}
```

### 4.3 事件（Rust → 前端）

| 事件名 | 载荷 | 用途 |
|---|---|---|
| `import://progress` | `{ file, index, total, stage }` | 导入进度 |
| `import://finished` | `{ succeeded: Book[], failed: { file, reason }[] }` | 导入结果汇总 |
| `import://duplicate` | `{ existing: Book, incoming: string }` | 疑似重复提示 |

> **设计取舍**：导入进度用**事件**而非命令返回值——导入是耗时操作（10 MB 文件解码 + 切章可能数百毫秒到数秒），必须异步推送。其余操作都是"请求—响应"式，用命令即可，**不滥用事件**。

### 4.4 契约的自动化

```rust
// src-tauri/src/lib.rs（示意）
let builder = tauri_specta::Builder::<tauri::Wry>::new()
    .commands(tauri_specta::collect_commands![
        list_books, pick_and_import, import_paths, delete_book, rename_book,
        open_book, load_chapter, save_progress,
        list_bookmarks, add_bookmark, remove_bookmark,
        get_settings, save_settings,
    ])
    .events(tauri_specta::collect_events![ImportProgress, ImportFinished]);
```

生成产物落到 `src/ipc/`，前端直接 `import { commands } from "./ipc/commands"`，获得完整类型提示。

**收益**：Rust 侧新增一个字段时，前端**编译期**就会报错提示未处理——这是双语言架构下最有效的护栏，也是本方案对抗"契约漂移"这个主要维护风险的核心手段。

## 5. 领域模型与存储

> 本节内容与 [上一版架构](archive/02-架构设计-v1-egui方案.md) 完全一致，不受 UI 框架更换影响。

### 5.1 领域模型

```rust
pub struct BookId(pub Uuid);

pub struct Book {
    pub id: BookId,
    pub title: String,
    pub author: Option<String>,
    pub source_name: String,
    pub source_encoding: String,
    pub byte_size: u64,
    pub chapter_count: u32,
    pub has_real_chapters: bool,
    pub content_hash: u64,
    pub added_at: Timestamp,
    pub last_read_at: Option<Timestamp>,
}

pub struct Chapter {
    pub index: u32,
    pub title: String,
    pub start: u64,          // 规范化正文中的字节偏移
    pub end: u64,
}

pub struct ReadingProgress {
    pub book_id: BookId,
    pub chapter_index: u32,
    pub char_offset: u32,    // ★ 章内字符偏移
    pub updated_at: Timestamp,
}
```

**进度为什么仍然存「字符偏移」**：它与 UI 框架无关。无论是分页还是滚动，字符偏移都是唯一稳定的语义锚点——换字号、换字体、换设备、甚至切换"分页 ↔ 滚动"阅读模式都不会失效。

### 5.2 磁盘布局

```
<app_data>/
├─ library.redb                    # 元数据（redb + postcard）
├─ books/<book_id>/content.txt     # 规范化 UTF-8 正文（唯一事实源）
├─ fonts/                          # 用户导入字体
└─ cache/                          # 可重建的缓存
```

各平台 `<app_data>`：Windows `%APPDATA%/PlainRead/`；安卓 `/data/data/<pkg>/files/`。

### 5.3 redb 表结构

| 表 | Key | Value |
|---|---|---|
| `books` | `BookId` | `Book` |
| `chapters` | `BookId` | `Vec<Chapter>`（整块 postcard） |
| `progress` | `BookId` | `ReadingProgress` |
| `bookmarks` | `Uuid` | `Bookmark` |
| `bm_by_book` | `(BookId, Uuid)` | `()` |
| `settings` | `&str` | `postcard` |

> 决策依据见 [ADR-002](adr/ADR-002-存储与索引格式.md)。切换 Tauri **不影响该决策**——Rust 侧依然要交叉编译，纯 Rust 依赖依然是优势。

## 6. 导入管线

> 同样属于 `reader-core`，不受 UI 框架影响。

```
选择文件（桌面：原生对话框 / 安卓：SAF）
   ↓ 后台线程处理，通过事件推送进度
   ↓ 1. 读前 64 KB → BOM 检查 → chardetng 猜测
   ↓ 2. encoding_rs 全量解码 → String
   ↓ 3. 规范化（换行统一 / 去 BOM / 去零宽字符 / 压缩空行 / 不做简繁与全半角转换）
   ↓ 4. 章节切分（L1–L4 四级 + 误判保护）
   ↓ 5. content_hash 查重
   ↓ 6. 写 books/<id>/content.txt
   ↓ 7. 写 redb（books + chapters）
完成 → 前端收到 import://finished → 刷新书架
```

## 7. 阅读器前端实现（本方案的"美观与好用"落点）

这一节取代了上一版的「分页引擎」。**排版质量由浏览器保证，我们的工作是把它用好。**

### 7.1 分页方案：CSS 多列

| 方案 | 评价 |
|---|---|
| A. 滚动模式 | 实现最简，但缺少"书感"；作为 1.0 的可选模式保留 |
| **B. CSS 多列分页** | ✅ **主方案**。真分页、翻页动画易做、技术成熟（大量网页阅读器采用） |
| C. JS 手动测量切页 | 重造轮子，且比引擎慢 |

核心 CSS：

```css
.reader-viewport {
  height: 100%;
  column-width: var(--rd-page-width);   /* 一屏一列 */
  column-gap: var(--rd-page-gap);
  column-fill: auto;                    /* ★ 必须：顺序填满再开下一列，而非各列均分高度 */
  will-change: transform;
}
```

翻页位移：`transform: translateX(calc(-1 * var(--rd-page) * var(--rd-page-stride)))`，配合 `transition` 实现动画。

> **关键细节**：`column-fill` 默认是 `balance`（各列等高），那会导致内容被均分而不是顺序分页。**必须显式设为 `auto`。**

### 7.2 中文排版 CSS（开箱即得的红利）

```css
.reader-content {
  font-family: var(--rd-font-family);      /* 系统字体，浏览器自动回退生僻字/繁体/emoji */
  font-size: var(--rd-font-size);
  line-height: var(--rd-line-height);
  letter-spacing: var(--rd-letter-spacing);
  text-indent: 2em;                        /* 首行缩进两字 */
  text-align: justify;
  line-break: strict;                      /* ★ CJK 禁则（标点不在行首/行尾） */
  text-spacing-trim: trim-start;           /* ★ 标点挤压（Chrome 123+，渐进增强） */
  text-autospace: normal;                  /* ★ 中西文自动间距（Chrome 120+） */
  word-break: normal;
  overflow-wrap: break-word;               /* 超长 URL / 英文单词兜底 */
  hyphens: none;
  hanging-punctuation: allow-end;          /* 仅 Safari 生效，写了无害 */
}
```

> ⚠️ **必须设置 `<html lang="zh-Hans">`**。这是 W3C 明确的前提：没有语言标注，`line-break` 与 `text-spacing-trim` 的部分行为不会生效。这是一个容易踩、又很难排查的坑。

**渐进增强策略**：`line-break: strict` 自 2020 年起广泛可用，属于**基础保障**；`text-spacing-trim` / `text-autospace` 需要较新的 Chromium，属于**加分项**——老设备上退化为普通渲染，不影响可用性。

### 7.3 进度锚点算法（唯一需要仔细写的核心逻辑）

这是整个前端里唯一有算法含量的部分。

**建立映射**：章节文本以 `<p>` 段落渲染。用 `TreeWalker` 顺序遍历文本节点并累加 `length`，即可建立「字符偏移 → (节点, 节点内偏移)」的映射。

```ts
// 保存：页索引 → 字符偏移（取当前页首个可见字符）
const offset = pageToCharOffset(viewportEl, pageIndex);

// 恢复：字符偏移 → 页索引
function charOffsetToPage(offset: number): number {
  const range = charOffsetToRange(contentEl, offset);   // TreeWalker 定位
  const rect = range.getBoundingClientRect();
  const left = rect.left - contentEl.getBoundingClientRect().left;
  return Math.round(left / pageStride);                 // 列索引 = 页索引
}
```

**为什么这样设计**：字号 / 行距 / 页边距 / 字体变化后，只需重新调用一次 `charOffsetToPage`，**阅读位置语义完全不变**。这就是"拖动字号滑块后仍然停在原来那句话"的实现方式。

**必须成立的不变式**：对任意页 `i`，`charOffsetToPage(pageToCharOffset(i)) === i`。这条以 Vitest 单元测试覆盖——它是上一版「进度往返」不变式的等价形式。

### 7.4 性能与边界

| 场景 | 处理 |
|---|---|
| 章节过长（如单章 5 万字） | 多列布局有性能开销。设阈值（约 2 万字），超过则自动降级为滚动模式并提示 |
| 翻页预取 | 当前章 ±1 章预加载文本，跨章翻页无感知延迟 |
| 翻页动画 | `transform` + `transition`，约 180–220 ms，GPU 加速。1.0 做平移 / 覆盖，仿真卷页留到 2.0 |
| 参数连续调整 | 改 CSS 变量触发的重排用 `requestAnimationFrame` 包裹，避免拖动滑块时的抖动 |

### 7.5 主题与视觉

用 CSS 变量实现，三套主题只需换一组变量值，且可做平滑过渡：

```css
:root[data-theme="paper"] { --rd-bg:#f5efe1; --rd-fg:#2f2a22; --rd-muted:#8a8272; }
:root[data-theme="white"] { --rd-bg:#ffffff; --rd-fg:#1a1a1a; --rd-muted:#8a8a8a; }
:root[data-theme="night"] { --rd-bg:#121212; --rd-fg:#b8b4ad; --rd-muted:#6b6862; }

:root {
  --rd-page-width: calc(100vw - var(--rd-margin-h) * 2);
  --rd-page-gap: calc(var(--rd-margin-h) * 2);
  --rd-page-stride: calc(var(--rd-page-width) + var(--rd-page-gap));
}
```

### 7.6 安全区（原 R2 风险的基本消失）

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">
```

```css
:root {
  --safe-top:    env(safe-area-inset-top, 0px);
  --safe-bottom: env(safe-area-inset-bottom, 0px);
  --safe-left:   env(safe-area-inset-left, 0px);
  --safe-right:  env(safe-area-inset-right, 0px);
}
.reader-viewport {
  padding: calc(var(--safe-top) + var(--rd-margin-v))
           calc(var(--safe-right) + var(--rd-margin-h))
           calc(var(--safe-bottom) + var(--rd-margin-v))
           calc(var(--safe-left) + var(--rd-margin-h));
}
```

**对比原方案**：上一版需要在 Android 侧读取 window insets、换算逻辑像素、再传到 Rust 侧参与排版计算。现在**一行 CSS 解决**，且刘海、挖孔、底部手势条、横屏左右安全区**全部自动适配**。这是本决策带来的一项被低估的收益。

## 8. 安卓落地

### 8.1 技术参数

| 项 | 取值 | 说明 |
|---|---|---|
| 外壳 | Tauri 2（`tauri android`） | 生成 `src-tauri/gen/android/` |
| `minSdk` | 24（Tauri 默认，按需覆盖为 26） | 需与 WebView 特性策略一起权衡 |
| `targetSdk` | 35 | |
| ABI | `arm64-v8a` + `x86_64`（上架前补 `armv7`） | 控制 APK 体积 |
| 渲染 | 系统 WebView（Chromium） | 不内置浏览器内核，APK 保持小体积 |

### 8.2 工程与可修改点

`tauri android init` 生成的工程中，`MainActivity.kt` **可以直接编辑**。需要原生侧配合的能力都放这里：

| 能力 | 实现 |
|---|---|
| 沉浸式全屏 | `WindowInsetsControllerCompat.hide(systemBars)` |
| 屏幕常亮 | 优先尝试 Web 的 `navigator.wakeLock.request('screen')`（**待验证安卓 WebView 支持度**）；失败则用 Kotlin 的 `FLAG_KEEP_SCREEN_ON` |
| 状态栏 / 导航栏图标明暗 | `WindowInsetsControllerCompat` 设置 |

### 8.3 文件导入的三个入口

| 入口 | 方案 | 体验 |
|---|---|---|
| 应用内导入按钮 | Tauri 官方 `dialog` 插件（移动端走 SAF） | 标准 |
| 系统「打开方式」 | `AndroidManifest.xml` 注册 `text/plain` 的 `VIEW` intent-filter | **最佳**，零权限弹窗 |
| 高级 SAF 需求 | 社区 `tauri-plugin-android-fs`（SAF URI 持久化、MediaStore） | 备用 |

> 导入后立即复制进应用私有目录，之后只读私有副本。**不申请 `MANAGE_EXTERNAL_STORAGE`**（会被应用商店拒审），不需要持久化 URI 授权，用户删除原文件也不影响阅读。

### 8.4 WebView 版本碎片化应对（本方案新增的主要外部风险）

| 措施 | 说明 |
|---|---|
| 构建层降级 | `vite.config.ts` 设置 `build.target: ['es2018', 'chrome90']`，避免新语法在老 WebView 上直接报错 |
| CSS 渐进增强 | 新特性（`text-spacing-trim` 等）只作为视觉加分，不作为功能依赖 |
| 启动检测 | 读取 `navigator.userAgent` 中的 Chromium 版本，低于阈值时关闭高级排版特性并提示更新 WebView |
| 规避高危特性 | 避免 `:has()`、容器查询等对老版本不友好的选择器，或提供 fallback |

### 8.5 生命周期

| 时机 | 动作 |
|---|---|
| 应用切后台 | 前端立即 `save_progress`（不等防抖）；Rust 侧强制 flush |
| 旋转 / 折叠屏 | CSS 变量与 `env(safe-area-inset-*)` 自动响应 → 重排 → 用锚点重新定位，**进度不丢** |
| 内存紧张 | WebView 被系统回收重建 → 前端重新 `open_book` 拉取会话状态，**进度从 redb 恢复** |

## 10. 测试策略

分工发生了变化：**排版正确性交给浏览器，我们的测试聚焦数据管线与锚点算法。**

| 层次 | 对象 | 方式 | 自动化 |
|---|---|---|---|
| 单元（Rust） | 编码识别 | UTF-8 / GBK / GB18030 / UTF-16LE / Big5 样本 | ✅ |
| 单元（Rust） | 文本规范化 | `\r\n` / BOM / 零宽字符 / 多余空行 | ✅ |
| 单元（Rust） | 章节切分 | 语料快照测试 + 误判保护 | ✅ |
| 单元（Rust） | 仓储 | 临时目录 redb，全表 CRUD 往返 | ✅ |
| 集成（Rust） | 导入全链路 | 样本文件 → 断言落盘与库记录 | ✅ |
| **单元（TS）** | **进度锚点** | `charOffsetToPage(pageToCharOffset(i)) === i` | ✅ |
| 单元（TS） | 翻页边界 | 首章首屏 / 末章末屏 / 空章节 | ✅ |
| 契约 | IPC 类型 | `tauri-specta` 生成物与 Rust 类型一致性（构建即校验） | ✅ |
| 手工 | 真机 | 安全区、手势、旋转、深浅色、老版本 WebView | ❌ |

### 保留的两条核心不变式（形式已调整）

| 不变式 | 原形式（v1） | 现形式（v3） |
|---|---|---|
| **不丢字** | 所有页拼接 == 规范化原文 | **数据层**：`load_chapter` 返回文本与 `content.txt` 的字节区间**逐字符一致**（渲染不丢字由浏览器保证） |
| **进度往返** | `page_of(pages[i].start_char) == i` | **前端**：`charOffsetToPage(pageToCharOffset(i)) === i` |

> 两条不变式的**语义完全保留**，只是实现位置从"自研分页引擎"搬到了"数据层 + 锚点算法"。这说明这两条约束是本质的，与 UI 框架无关。
